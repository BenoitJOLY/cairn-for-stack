# PLAN — HéStack V4

Ce fichier est la référence unique et persistante du projet. Toute session de travail doit le lire avant d'agir et le mettre à jour avant de terminer. Il remplace les résumés de conversation comme source de vérité.

## Règles de fonctionnement (non négociables)

1. **Git est le filet de sécurité.** Chaque changement de code = un commit séparé, avec un message clair. Aucun changement n'est fait hors commit. En cas de doute sur l'état d'un fichier, `git diff` / `git log` font foi — pas la mémoire de la conversation.
2. **Aucune affirmation de succès sans preuve.** Il n'y a ni navigateur, ni Node/npm, ni Moodle installés dans l'environnement d'exécution. Donc :
   - Le code peut être relu et vérifié statiquement (syntaxe, cohérence, structure XML attendue).
   - Le fonctionnement réel (import Moodle, PRT, score, feedback affiché) ne peut être confirmé que par l'utilisateur, dans son propre Moodle.
   - Un type n'est marqué `✅ validé` que **après retour explicite de l'utilisateur**, jamais avant.
3. **Un type à la fois.** On ne commence pas le type suivant tant que le précédent n'est pas `✅ validé` ou explicitement mis de côté par l'utilisateur.
4. **Pas de gros commit fourre-tout.** Un commit = un type, ou une action isolée (ex: split d'un fichier sans changement de comportement).

## Direction architecturale (décidée le 2026-07-04)

- **Tout ce qui sort des modales de configuration est du JSON** (déjà le cas : `questions[qid]` + `questions[qid].state`, sérialisés en JSON dans localStorage / fichier `.hestack`).
- **Le XML Moodle/STACK n'est qu'une compilation finale**, dérivée du JSON, générée à l'export (et aujourd'hui aussi à chaque clic sur "Enregistrer" — voir Problème connu #1 ci-dessous).
- **Un fichier JS par type de question**, chacun < 1000 lignes, pour remplacer le monolithe `generators.js`. Convention de nommage déjà utilisée pour les types "math" (`gen-math-complexe.js`, `gen-math-calcul.js`, etc.) — **fait le 2026-07-05** pour les 18 types restants (voir tableau "État par type" ci-dessous), split mécanique sans changement de comportement (commit `7e3dc29`). `js/generators.js` ne contient plus que les helpers partagés (`wrapFb`, `sanitizeMaxima`, `algPrtNode`, `ALG_FB_DEFS`/`_algFbId`/`_algFb`).

## Problèmes connus

1. **[CORRIGÉ le 2026-07-04, cause racine réelle du "complètement cassé"] Le bloc `#hs-state` (signature JSON cachée pour le round-trip, injectée dans `questiontext` par `buildXML()` js/app.js) contenait du HTML réel non échappé** (le champ `html` = `innerHTML` de l'éditeur, avec les balises des chips). Seules les fermetures `</` étaient neutralisées (`<\/`) ; les balises d'OUVERTURE (`<span>`, `<svg>`, `<use>`...) restaient réelles. Résultat : quand Moodle affiche ce `questiontext` en HTML, le navigateur ouvre pour de vrai ces balises imbriquées (jamais refermées, puisque leurs fermetures étaient du texte inerte) — le vrai `</span>` ajouté juste après le bloc (censé refermer `#hs-state`, `display:none`) se retrouve alors à refermer une balise interne à la place. `#hs-state` reste donc ouvert et **avale tout l'énoncé visible qui suit dans le DOM** → la question entière (banner, énoncé, cases à cocher) devient invisible/cassée. Confirmé avec le cas Cases à cocher rapporté par l'utilisateur.
   **Premier correctif (insuffisant, rejeté par l'utilisateur)** : encodage complet des chevrons `<`/`>` en entités HTML dans le span caché — techniquement sûr, mais l'utilisateur a exigé que `<questiontext>` ne contienne **plus jamais** que l'énoncé et les placeholders `[[input:ansX]][[validation:ansX]]`, rien d'autre.
   **Deuxième correctif (insuffisant, rejeté par l'utilisateur)** : signature déplacée dans `<questiondescription>` en texte XML plat. Erreur : ce champ EST affiché à l'enseignant (banque de questions, formulaire d'édition) — l'utilisateur a vu le JSON brut entier s'afficher là où il attendait juste « Généré avec HéStack V2 | hestack-types:checkbox ».
   **Correctif final appliqué** : la signature `_hsState` (JSON encodé en **base64**, via `btoa(unescape(encodeURIComponent(s)))`) est sortie de tout champ de question et placée dans un **commentaire XML** `<!-- hestack::v1::... -->`, ajouté juste après `</questiondescription>` et avant `</question>`. Un commentaire XML n'est rendu nulle part, ni côté élève ni côté enseignant — c'est le seul emplacement qui ne pouvait pas casser l'affichage. Le base64 évite aussi tout souci d'échappement XML et la séquence interdite `--` dans un commentaire. `<questiontext>` ne contient que l'énoncé + placeholders, `<questiondescription>` ne contient que le libellé court `Généré avec HéStack V2 | hestack-types:...`. Le lecteur (`js/stack-import.js`) cherche d'abord ce commentaire (regex `<!--\s*hestack::v1::([A-Za-z0-9+/=]+)\s*-->`, décodage `atob` + `decodeURIComponent(escape(...))`), avec les deux anciens formats (`<questiondescription>` texte plat, span dans `<questiontext>`, `<idnumber>`) conservés comme fallbacks pour réimporter d'anciens exports.
   **Non testé en Moodle réel — priorité n°1 à valider par l'utilisateur.**

2. **[CORRIGÉ le 2026-07-04, candidat au rôle de cause racine "beaucoup de types cassés"] `buildQuestionText()` (js/editor.js:416) enveloppait le `textFrag` de chaque question dans un `<span>` superflu avant de l'insérer dans le texte de l'énoncé.** Or `textFrag` commence quasi systématiquement par un `<div>` (bandeau "Q1 — ..."), un élément de bloc invalide à l'intérieur d'un `<span>` (inline) — confirmé visuellement par l'utilisateur sur le type `checkbox` (span visible autour du bloc généré dans le XML exporté, absent du contenu attendu). Comme `buildQuestionText()` est utilisé pour TOUS les types de question, ce bug touchait potentiellement l'ensemble des exports, pas seulement checkbox.
   **Correctif appliqué** : remplacement du chip par le contenu d'un `<template>` (`chip.replaceWith(tpl.content)`) au lieu d'un `<span>` wrapper — insère les nœuds du fragment directement, sans enveloppe.
   **Non testé en Moodle réel — à valider par l'utilisateur, en particulier sur le type `checkbox` qui a servi à détecter le bug.**

3. **[CORRIGÉ le 2026-07-04] Étape "Prévisualisation & Édition avant export XML" (`js/verif.js`, modale `verifModal`) corrompait le XML.** Le flux était : `buildXML()` (js/app.js) produit un XML correct → `openVerifModal()` reparse ce XML avec `DOMParser`, reconstruit une interface de zones `contenteditable` → au clic sur "Télécharger", `doDownload()` (verif.js:200) réextrait le contenu de ces zones et re-sérialise un nouveau XML via `XMLSerializer` + une série de correctifs regex (CDATA, entités, cas spéciaux composition/JSX/DOI). Ce roundtrip parse→édition DOM→re-sérialisation perdait ou corrompait de l'information silencieusement (balises stack cachées, marqueurs ENONCE-START/END...) — c'est très probablement la cause du rapport "questions importables mais cassées" du 2026-07-04.
   **Correctif appliqué** : `confirmAndPreview()` (js/app.js) télécharge maintenant directement `built.xml` (sortie de `buildXML()`), sans passer par `openVerifModal()`. `js/verif.js` reste dans le dépôt mais n'est plus appelé dans le flux normal (changement réversible, choisi comme "bypass" plutôt que suppression complète). Bouton renommé "Confirmer et exporter" (`lang/fr.js`, `lang/en.js`).
   **Non testé en Moodle réel — à valider par l'utilisateur.**

7. **[CORRIGÉ le 2026-07-04] Le clavier virtuel "Aide à la saisie" (Algébrique/Numérique/Unités) ne fonctionnait plus dans Moodle.** Son bloc `[[script type="module"]]...[[/script]]` contient du JS littéral avec de vrais `<`, `>`, `&&`. Or `buildQuestionText()` et `stripMathDivs()` font toutes deux un aller-retour DOM (`.innerHTML =` puis `.innerHTML` lu en retour) sur le texte de la question — un navigateur échappe automatiquement `<`/`>`/`&` en entités lors de la sérialisation, ce qui corrompait le JS (`&gt;` au lieu de `>`, `&&` → `&amp;&amp;`), rendant le script invalide. Confirmé avec un export réel montrant ces entités dans le `[[script]]` du numérique.

Même technique que les marqueurs `ENONCE-START/END` déjà utilisés dans le code.
   **✅ Validé par l'utilisateur le 2026-07-04.**

### Phase 1 — Consolidation et stabilisation

Objectif : rendre le cœur de HéStack fiable avant toute extension serveur ou IA. Contient l'audit round-trip ci-dessus (1.1), ses corrections (1.2), les tests XML Moodle/STACK (1.3, voir tableau "État par type" ci-dessus pour les résultats à jour), et le gel des formats JSON (1.4, à faire une fois les types audités — base du futur prompt système IA de la Phase 4).

### Phase 2 — Infrastructure serveur

Objectif : sortir du modèle localStorage/fichier local pour un usage institutionnel.

| Ressource | Spécification | Priorité |
|---|---|---|
| Hébergement statique | nginx, ~500 Mo, HTTPS | Indispensable |
| Conteneur Goemaxima | 1 vCPU, 512 Mo RAM, port REST | Indispensable |
| Backend API | 1 vCPU, 1 Go RAM, Node.js ou Python/FastAPI | Indispensable |

| Authentification | ProConnect / ENT académique | Indispensable |

Ressources à soumettre à la forge des numériques. ⚠️ Les données pédagogiques ne doivent pas transiter par des services IA externes (OpenAI, Anthropic) sans accord institutionnel explicite.

### Phase 3 — Intégration Moodle / LTI 1.3

Objectif : HéStack accessible depuis Moodle sans installation complexe. Architecture retenue : LTI 1.3 + plugin local Moodle minimal — HéStack comme outil externe LTI 1.3, Deep Linking (insertion directe dans un cours Moodle), plugin local Moodle (~50 lignes PHP) pour l'enregistrement automatique de l'outil, API Web Services Moodle pour push/pull vers la banque de questions STACK, Goemaxima pour la validation Maxima temps réel dans l'éditeur Expert.

Statut : aucune étape commencée — squelette backend LTI 1.3 (Node.js), handshake LTI 1.3/OIDC, plugin local Moodle PHP, connexion API Web Services Moodle, push/pull question banque Moodle, proxy Goemaxima.

### Phase 4 — Assistant IA pédagogique

Objectif : l'enseignant dépose son cours ou TP, l'IA propose des questions HéStack configurées.

Flux cible : (1) l'enseignant dépose un document (PDF/DOCX/TXT) ; (2) HéStack extrait le texte côté client (PDF.js) ; (3) envoi à l'API IA avec un prompt système décrivant chaque module + son format JSON ; (4) l'IA retourne une liste structurée (type, justification pédagogique, JSON pré-rempli) ; (5) l'enseignant valide chaque suggestion → question créée dans l'éditeur ; (6) génération XML habituelle.

Prérequis bloquants : formats JSON documentés (après Phase 1.4, 🔲), accès API IA institutionnelle (Phase 2, 🔲), extraction texte PDF (PDF.js à intégrer, 🔲).

Statut : aucune étape commencée — modale "Analyser un document" (UI + upload), intégration PDF.js, rédaction du prompt système IA (après gel des formats 1.4), connexion API Albert/proxy IA, rendu des suggestions avec aperçu, injection des questions approuvées dans l'éditeur.
