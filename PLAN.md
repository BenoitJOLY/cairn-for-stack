## Règles de fonctionnement (non négociables)

1. **Git est le filet de sécurité.** Chaque changement de code = un commit séparé, avec un message clair. Aucun changement n'est fait hors commit. En cas de doute sur l'état d'un fichier, `git diff` / `git log` font foi — pas la mémoire de la conversation.
2. **Aucune affirmation de succès sans preuve.** Il n'y a ni navigateur, ni Moodle installés dans l'environnement d'exécution. Donc:
 - Le code peut être relu et vérifié statiquement (syntaxe, cohérence, structure XML attendue).
 - **Depuis le 2026-07-20, Node/npm sont disponibles dans l'environnement d'exécution** (voir chantier "Découplage DOM + tests unitaires" ci-dessous) : `node -e "require('./js/gen-xxx.js')"` permet de vérifier qu'un fichier parse, et `npm test` exécute la suite `test/unit/*.test.js` (434 tests) qui vérifie la logique pure des générateurs (`gen*Core`). Cela reste une vérification de cohérence interne du JS/Maxima généré, PAS une exécution réelle dans un navigateur ni dans STACK/Moodle.
 - Le fonctionnement réel (rendu navigateur, import Moodle, PRT, score, feedback affiché) ne peut être confirmé que par l'utilisateur, dans son propre Moodle — `npm test` qui passe ne vaut pas `✅ validé`.
 - Un type n'est marqué `✅ validé` que **après retour explicite de l'utilisateur**, jamais avant.
3. **Un type à la fois.** On ne commence pas le type suivant tant que le précédent n'est pas `✅ validé` ou explicitement mis de côté par l'utilisateur.
4. **Pas de gros commit fourre-tout.** Un commit = un type, ou une action isolée (ex: split d'un fichier sans changement de comportement).

## Découplage DOM + tests unitaires (2026-07-20)

Chantier multi-session, désormais complet pour sa partie conversion, terminé le 2026-07-20.

- **Objectif** : chaque `js/gen-*.js` expose désormais `genXxx(X)` (wrapper impur, lit `document`/globals) et `genXxxCore(X, p, deps)` (cœur pur : aucun accès DOM, dépendances externes injectées via `deps` avec repli sur les globals réels si non fournies — `I18N`, `buildPrtXml`, `wrapFb`, `_mkFbGen`, `buildKbdStackHTML`, etc.). Permet d'appeler et de tester la logique de génération XML/Maxima depuis Node, sans DOM ni navigateur.
- **Portée** : les 43 fichiers `js/gen-*.js` du dépôt suivent maintenant ce pattern (dernier converti : `js/gen-optique.js`, 11 paires wrapper/cœur, le plus gros fichier du projet — voir aussi point 1/3 ci-dessus, sa taille reste un problème à part entière).
- **Tests** : `test/unit/*.test.js`, lancés via `npm test` (`node --test`). 434 tests au total, couvrant les cœurs purs de la plupart des fichiers convertis (structure du XML généré via un vérificateur de balises équilibrées, présence des bons champs par scénario/mode, propagation correcte des paramètres).
- **Audit de régression ancien-code vs nouveau-code** : pour vérifier que la conversion n'a introduit aucun changement de comportement, un harnais Node (fake `document` léger + `vm` pour rejouer l'ancien code via `git show <hash-avant-conversion>^:js/gen-xxx.js`) a comparé la sortie AVANT/APRÈS sur des entrées identiques pour **14 des 36 fichiers convertis à l'époque de l'audit**. Deux bugs réels trouvés et corrigés (commit `3a58059`) :
  - `js/gen-units.js` : la conversion avait supprimé des lectures DOM mortes (`v('un-tol')`, `resolveFb('un-fbc'/'un-fbe', ...)`) qui avaient un effet de bord légitime (pré-remplissage des textarea si vides) — restaurées dans le wrapper.
  - `js/gen-numerical.js` : une ligne d'espace blanc dans un template littéral avait été perdue pendant la conversion — restaurée (piège rencontré : le fichier est en fin de ligne CRLF, un remplacement de chaîne naïf sur `\n` échoue silencieusement).
  - **Pattern partagé corrigé dans 3 fichiers** (`gen-units.js`, `gen-algebraic.js`, `gen-numerical.js`) : la dépendance `buildKbdStackHTML` avait été hissée en résolution *eager* (`var xxx_D = deps.xxx || xxx;` en tête du cœur) alors que le code d'origine ne l'appelait que *lazily*, dans la branche conditionnelle `useKbd ? ... : ''` — un cœur pur appelé sans cette dépendance plantait même quand la branche n'était pas empruntée. Corrigé en inlinant le repli `(deps.xxx || xxx)` au point d'appel plutôt qu'en tête de fonction.
  - Après ces 3 correctifs : `npm test` reste à 434/434, `node -e "require(...)"` confirme que les 43 fichiers parsent.
  - **22 fichiers restants non audités par cette méthode** (liste et harnais laissés dans le scratchpad de la session, non committés) — opportunité de suite documentée mais non urgente : le risque de régression silencieuse est jugé faible (le pattern de conversion est mécanique et déjà éprouvé sur 21 fichiers sans bug), mais reste un point ouvert si un comportement bizarre est signalé sur un type converti et non encore audité.
- **Limite fondamentale, à ne jamais perdre de vue** : `npm test` vérifie la logique JS/Maxima *pure* (le code qui construit les chaînes XML/Maxima), pas le rendu navigateur ni le comportement réel dans STACK/Moodle. Un type peut avoir 100% de ses tests unitaires au vert et rester non fonctionnel une fois importé dans Moodle — les statuts `✅ validé` du tableau "État par type" ci-dessous restent la seule source de vérité sur le fonctionnement réel, inchangés par ce chantier.

## Backend auto-hébergé NAS : login + protection anti-piratage du code (ouvert 2026-07-23)

**Objectif** : (1) réserver l'usage de StackForge à un groupe fermé de comptes créés par l'auteur (pas d'auto-inscription), et (2) empêcher que la logique de génération (les ~43 fichiers `js/gen-*.js` — le cœur métier Maxima/PRT, ce qui a de la valeur) ne soit distribuée en clair au navigateur. Aujourd'hui l'app est 100% statique : n'importe qui avec l'URL peut l'utiliser ET copier tout `js/`.

**Constat de départ, à ne jamais perdre de vue** : rien qui s'exécute dans le navigateur ne peut être rendu réellement inaccessible (le JS doit être lisible/exécutable par le client). Minifier/obfusquer ne fait que ralentir une copie occasionnelle. La seule protection réelle est de ne **jamais envoyer** le code des générateurs au client — de le faire tourner côté serveur et de ne renvoyer que le XML résultat.

**Décisions prises avec l'utilisateur (2026-07-23)** :
- Comptes en **liste fermée**, créés uniquement par l'auteur (pas de formulaire d'auto-inscription, pas de mot de passe oublié par email à gérer).
- Le login protège **toute l'app**, pas seulement l'export XML — l'interface (formulaires de config des ~40 types) n'est servie qu'après authentification.
- Hébergement visé : le **NAS Synology de l'auteur**, en réutilisant le pattern Docker déjà validé pour `stack-api`/`goemaxima` (voir chantier "Connexion Maxima réelle" ci-dessus) plutôt que la Phase 2 institutionnelle plus lourde décrite dans la "Feuille de route institutionnalisation" (PostgreSQL 5 Go, ProConnect/ENT, forge des numériques — hors de propos pour un usage NAS personnel/petit groupe).

**Architecture cible** :
- Nouveau conteneur Docker `stackforge-server` (Node/Express) sur le NAS, servi derrière un reverse proxy HTTPS (à mettre en place si pas déjà existant pour un autre service du NAS).
- Authentification par **session cookie httpOnly + secure** (pas de JWT en localStorage, vulnérable au XSS). Comptes stockés côté serveur (fichier JSON ou SQLite suffisant vu le volume attendu — quelques dizaines de comptes, pas besoin de PostgreSQL), mots de passe hashés (bcrypt/argon2). Un compte = créé manuellement par l'auteur (script CLI ou route admin protégée), jamais par inscription libre.
- Middleware serveur : toute requête vers les fichiers statiques (`index.html`, `js/*`, `css/*`) ou l'API exige une session valide.
- Les fichiers `js/gen-*.js` (et tout ce qui contient de la logique métier) **quittent le dossier public servi au navigateur** et vivent dans un dossier serveur non exposé (ex. `server/generators/`). Le serveur les charge en interne uniquement.
- Nouvel endpoint `POST /api/generate` : reçoit `{type, params}` (JSON), appelle en interne `genXxxCore(params, deps)` (déjà pur, déjà exécutable sous Node — voir chantier "Découplage DOM + tests unitaires" du 2026-07-20, c'est exactement le point qui rend cette migration faisable sans réécrire les générateurs) et renvoie le XML/PRT généré. Le wrapper impur `genXxx` reste côté client uniquement pour lire le DOM et construire `params` — il n'exécute plus la génération lui-même.

**Ce qui ne change pas** : l'UI (formulaires, aperçu) reste dans le navigateur — ce n'est pas elle qui a de la valeur. `localStorage`/fichier `.stackforge` restent le mode de sauvegarde des projets (pas de migration vers une BDD serveur, hors scope de ce chantier).

**Étapes proposées, une à la fois avec validation avant de passer à la suivante (règle #3)** :
1. **[✅ validé sur le NAS, 2026-07-23]** Serveur Express minimal (dossier `server/`, non un nouveau dépôt — voir décision ci-dessous), sert `index.html`/`js`/`css`/`lang`/`lib`/`assets`/`depot.html` tels quels via une **liste blanche explicite** (pas de `express.static` sur toute la racine du dépôt — celle-ci contient `PLAN.md`, `test/`, des scripts scratch (`_extract*.py`, `_ref_*`), qui ne doivent jamais être servis). Fichiers : `server/server.js` (whitelist + route `/healthz`), `server/package.json` (dépendance `express` seule), `Dockerfile` **à la racine du dépôt** (déplacé depuis `server/Dockerfile` : le wizard "Ajouter depuis un dossier" de Synology Container Manager rejette un Dockerfile situé dans un sous-dossier — build : `docker build -t stackforge-server .`), `docker-compose.yml` à la racine (`build: .` + port `3000:3000`), `.dockerignore` à la racine. `node_modules/` ajouté au `.gitignore` racine. **Testé en local** (`node server/server.js` + `curl`) : `/`, `/healthz`, `/js/app.js`, `/css/style.css`, `/lib/katex/katex.min.js` → 200 ; `/PLAN.md`, `/server/server.js` → 404 comme attendu. **Déploiement NAS** : le wizard manuel "Image → Ajouter depuis un dossier" de Container Manager a échoué 3 fois de suite ("Le format de Dockerfile fichier(s) est incorrect.", y compris Dockerfile à la racine et sélection au niveau dossier) — abandonné. Bascule vers la fonctionnalité **"Projet"** de Container Manager (basée sur `docker-compose.yml`), qui construit et lance le conteneur en une fois : **succès**. **Décision (2026-07-23)** : le serveur vit dans le même dépôt (`server/`), pas un nouveau projet séparé — il doit `require()` directement les cœurs purs `genXxxCore` des fichiers `gen-*.js` existants, et `PLAN.md` doit rester la référence unique. Vérifié au passage : `github.com/BenoitJOLY/stackforge` répond 404 en anonyme, donc le dépôt est bien privé (sinon `js/gen-*.js` serait déjà public indépendamment de tout backend).

**Limite assumée, à ne pas perdre de vue** : le login empêche l'accès non autorisé, mais un compte légitime pourrait toujours, techniquement, reconstituer une partie de la logique en multipliant les appels à `/api/generate` avec des paramètres variés et en observant les sorties — aucune API ne protège de ça, seulement la confiance dans le groupe fermé de comptes et du rate limiting. À mettre en regard des décisions de gouvernance/licence déjà prises (voir journal du 2026-07-xx : double licence AGPL-3.0 + commerciale, mainteneur unique) — protection technique et protection juridique se complètent, aucune des deux n'est suffisante seule.

Le split des fichiers monolithiques (dont `index.html`) reste en attente pour la raison documentée le 2026-07-23 : plus pertinent une fois cette architecture serveur en place.

## Direction architecturale (décidée)

- **Tout ce qui sort des modales de configuration est du JSON** (déjà le cas: `questions[qid]` + `questions[qid].state`, sérialisés en JSON dans localStorage / fichier `.stackforge`).
- **Le XML Moodle/STACK n'est qu'une compilation finale**, dérivée du JSON, générée à l'export (et aujourd'hui aussi à chaque clic sur "Enregistrer" — voir Problème connu #1 ci-dessous).
- **Un fichier JS par type de question**, chacun < 1000 lignes, pour remplacer le monolithe `generators.js`. ## Problèmes connus

1.**[CORRIGÉ, cause racine réelle du "complètement cassé"] Le bloc `#hs-state` (signature JSON cachée pour le round-trip, injectée dans `questiontext` par `buildXML` js/app.js) contenait du HTML réel non échappé** (le champ `html` = `innerHTML` de l'éditeur, avec les balises des chips). Seules les fermetures `</` étaient neutralisées (`<\/`); les balises d'OUVERTURE (`<span>`, `<svg>`, `<use>`...) restaient réelles. Résultat: quand Moodle affiche ce `questiontext` en HTML, le navigateur ouvre pour de vrai ces balises imbriquées (jamais refermées, puisque leurs fermetures étaient du texte inerte) — le vrai `</span>` ajouté juste après le bloc (censé refermer `#hs-state`, `display:none`) se retrouve alors à refermer une balise interne à la place. `#hs-state` reste donc ouvert et **avale tout l'énoncé visible qui suit dans le DOM** → la question entière (banner, énoncé, cases à cocher) devient invisible/cassée. Confirmé avec le cas Cases à cocher rapporté par l'utilisateur.
**Premier correctif (insuffisant, rejeté par l'utilisateur)**: encodage complet des chevrons `<`/`>` en entités HTML dans le span caché — techniquement sûr, mais l'utilisateur a exigé que `<questiontext>` ne contienne **plus jamais** que l'énoncé et les placeholders `[[input:ansX]][[validation:ansX]]`, rien d'autre.
**Deuxième correctif (insuffisant, rejeté par l'utilisateur)**: signature déplacée dans `<questiondescription>` en texte XML plat. Erreur: ce champ EST affiché à l'enseignant (banque de questions, formulaire d'édition) — l'utilisateur a vu le JSON brut entier s'afficher là où il attendait juste « Généré avec StackForge V2 | stackforge-types:checkbox ».
**Correctif final appliqué**: la signature `_hsState` (JSON encodé en **base64**, via `btoa(unescape(encodeURIComponent(s)))`) est sortie de tout champ de question et placée dans un **commentaire XML** `<!-- stackforge::v1::... -->`, ajouté juste après `</questiondescription>` et avant `</question>`. Un commentaire XML n'est rendu nulle part, ni côté élève ni côté enseignant — c'est le seul emplacement qui ne pouvait pas casser l'affichage. Le base64 évite aussi tout souci d'échappement XML et la séquence interdite `--` dans un commentaire. `<questiontext>` ne contient que l'énoncé + placeholders, `<questiondescription>` ne contient que le libellé court `Généré avec StackForge V2 | stackforge-types:...`. Le lecteur (`js/stack-import.js`) cherche d'abord ce commentaire (regex `<!--\s*stackforge::v1::([A-Za-z0-9+/=]+)\s*-->`, décodage `atob` + `decodeURIComponent(escape(...))`), avec les deux anciens formats (`<questiondescription>` texte plat, span dans `<questiontext>`, `<idnumber>`) conservés comme fallbacks pour réimporter d'anciens exports.
**Non testé en Moodle réel — priorité n°1 à valider par l'utilisateur.**

2.**[CORRIGÉ, candidat au rôle de cause racine "beaucoup de types cassés"] `buildQuestionText` (js/editor.js:416) enveloppait le `textFrag` de chaque question dans un `<span>` superflu avant de l'insérer dans le texte de l'énoncé.** Or `textFrag` commence quasi systématiquement par un `<div>` (bandeau "Q1 —..."), un élément de bloc invalide à l'intérieur d'un `<span>` (inline) — confirmé visuellement par l'utilisateur sur le type `checkbox` (span visible autour du bloc généré dans le XML exporté, absent du contenu attendu). **Correctif appliqué**: remplacement du chip par le contenu d'un `<template>` (`chip.replaceWith(tpl.content)`) au lieu d'un `<span>` wrapper — insère les nœuds du fragment directement, sans enveloppe.
**Non testé en Moodle réel — à valider par l'utilisateur, en particulier sur le type `checkbox` qui a servi à détecter le bug.**

3.**[CORRIGÉ] Étape "Prévisualisation & Édition avant export XML" (`js/verif.js`, modale `verifModal`) corrompait le XML.** Le flux était: `buildXML` (js/app.js) produit un XML correct → `openVerifModal` reparse ce XML avec `DOMParser`, reconstruit une interface de zones `contenteditable` → au clic sur "Télécharger", `doDownload` (verif.js:200) réextrait le contenu de ces zones et re-sérialise un nouveau XML via `XMLSerializer` + une série de correctifs regex (CDATA, entités, cas spéciaux composition/JSX/DOI). **Non testé en Moodle réel — à valider par l'utilisateur.**

   - **[CORRIGÉ, ✅ validé par l'utilisateur en Moodle réel] Bug `a=0` (et équivalents) — coefficient de plus haut degré / coefficient d'étude ne peut jamais valoir 0.** Ajout d'un flag `excludeZero: true` sur `deg2.a`, `deg3.a` et `exp.B` dans `GGB_MODELS` (`js/geogebra-ui.js`). `ggbCoeffExpr` : en mode aléatoire, énumère les valeurs discrètes possibles (min/max/step fixés à l'export, seul le tirage est aléatoire côté Moodle), retire 0 (tolérance epsilon pour le pas `0.2` de `exp.B`), et tire un ÉLÉMENT de l'ensemble restant via la syntaxe Maxima `rand({v1,v2,...})` (`rand()` sur un ensemble retourne un élément, pas un index) au lieu de la formule linéaire `min+step*rand(n)`. En mode valeur fixe, une saisie explicite de 0 par l'enseignant est aussi corrigée (décalée au pas le plus proche) plutôt que laissée passer. Correction annexe : le calcul de la valeur médiane par défaut de l'aperçu Config (`ggbPreviewOverrideVal`) évitait déjà d'atterrir exactement sur 0 pour ces coefficients (les plages `-4..4`/`-2..2`/`-1..1` sont symétriques, donc `(min+max)/2 = 0`).
   - **[CORRIGÉ, ✅ validé par l'utilisateur en Moodle réel] Feedbacks PRT non pédagogiques — l'élève ne savait pas où était son erreur ni comment la corriger.** Ancien comportement : un seul nœud PRT agrégeant un score global (`ggb_sc_X`), feedback en cas d'échec = pourcentage + révélation brute de tous les objets GeoGebra internes attendus (`gVx`, `gR1`, etc., noms illisibles pour l'élève), sans indiquer quel critère précis avait échoué. **Fix** (`js/gen-geogebra.js`) : restructuration en PRT séquentiel, un nœud par critère de sortie (calqué sur le pattern `_oscNode`/`_oscSimplePair` de `gen-oscilloscope.js`), chaque nœud testant `ggb_ok_X[i+1] = 1` (le tableau `ggb_ok_X` et ses gardes `numberp`/`stringp` par critère, déjà validés Moodle, sont conservés à l'identique) et enchaînant vers le nœud suivant que le critère soit correct ou non (`truenextnode`/`falsenextnode` identiques, sauf dernier nœud `-1`), afin que tous les critères soient évalués et que leurs feedbacks s'accumulent dans le retour à l'élève. Chaque critère correct apporte `1/N` du score (`truescoremode: '+'`), un échec n'apporte ni ne retire de points (`falsescoremode: '-'`, `falsescore: 0`). Chaque diagnostic des 4 modèles préréglés (`GGB_MODELS.*.diagnostics` dans `js/geogebra-ui.js`) a reçu un `desc` (libellé court, ex. "Abscisse du sommet de la parabole") et un `hint` (piste de correction sans révéler la valeur exacte, ex. "Repérez le point le plus haut... et comparez son abscisse à la valeur de h") propagés dans `st.outputs` par `ggbApplyModel`. Nouvelle fonction `ggbBuildOutputFeedback(o)` construit, par sortie : succès = libellé + confirmation ; échec = libellé + piste pédagogique (`o.hint`) si disponible, sinon repli sur la révélation de la valeur attendue (mode Expert/custom, sans métadonnée de modèle). `ggbBuildFeedbackHtml` (utilisée par l'aperçu Config) conservée mais redéfinie comme concaténation de tous les `ggbBuildOutputFeedback` — l'aperçu n'exécutant pas réellement le PRT, il affiche à titre indicatif le texte de chaque critère plutôt qu'un seul verdict global. Nouvelles clés I18N `ggb.fb_crit_ok`/`ggb.fb_crit_ko`/`ggb.fb_expected_value` ajoutées dans `lang/fr.js`/`lang/en.js` (le contenu `desc`/`hint` des diagnostics lui-même reste en français brut dans `GGB_MODELS`, cohérent avec les libellés de coefficients déjà non-i18n'isés du même fichier). Anciennes clés `ggb.fb_ok_title`/`ggb.fb_wrong`/`ggb.prt_node0_desc` laissées en place (inoffensives, plus référencées par le nouveau code sauf `prt_node0_desc` réutilisée comme repli de description de nœud en mode Expert).

36.**[CORRIGÉ, ✅ Validé Moodle réel] Composition Libre — le bloc JSXGraph (éditeur riche élève) apparaissait vide dans le XML exporté, malgré un fichier de référence fonctionnel.** Trois bugs distincts corrigés dans `js/gen-composition.js` avant d'atteindre l'état validé :
 - **Bug 1 — `input-ref` ne correspondait pas au nom réel de l'input.** `buildCompositionJSX` codait en dur `input-ref-ans1="refAns1"`, alors que l'input STACK est nommé `ans{X}_html` (X = numéro de question) — dès que X≠1 ou que le nom ne matchait pas exactement, STACK ne résolvait pas le binding. **Fix**: paramétrage de `buildCompositionJSX(height, X)` avec `input-ref-ans${X}_html="refAns1"`.
 - **Bug 2 — échappement HTML du JS brut par les allers-retours DOM.** `buildQuestionText` (`js/editor.js`) et `moodleLatex`/`stripMathDivs` (`js/app.js`) font passer tout le texte de question par `innerHTML`, ce qui transforme le JS littéral (`>`, `&&`) en entités HTML (`&gt;`, `&amp;&amp;`) et casse le script JSXGraph. **Fix**: reprise du pattern déjà établi pour `gen-algebraic.js` (marqueur `<!--HS-KBD:{X}-->` inséré dans `textFrag`, code JS réel transmis via un champ `kbdRaw` réinjecté tel quel par `app.js` après tous les allers-retours DOM).
 - **Bug 3 — deux erreurs de validation serveur STACK.** `manualgraded:1` rejeté (`inputbase.class.php::validate_extra_options` exige un booléen PHP réel via `is_bool()`, pas `1`/`0`) → corrigé en `manualgraded:true`. `<tans></tans>` vide rejeté par `edit_stack_form.php` (modèle de réponse non-blanc exigé même si `notes.class.php` l'ignore ensuite et renvoie toujours `'true'`) → corrigé en `<tans>1</tans>`.
 - **Bug 4 (régression du chantier i18n #34) — après les 3 fixes ci-dessus, le JSXGraph restait vide.** Cause : la migration i18n avait remplacé les textes français en dur de `buildCompositionJSX` par des appels `I18N.t('comp.xxx')`, mais **sans** les envelopper dans `${...}` d'interpolation du template literal — le code généré contenait donc littéralement la chaîne `I18N.t('comp.xxx')`, exécutée telle quelle dans la page Moodle où l'objet global `I18N` de StackForge n'existe pas → `ReferenceError` dès la première occurrence, script entier interrompu. **Fix**: les 16 occurrences concernées (lignes ~173-357) enveloppées en `${JSON.stringify(I18N.t('...'))}` pour résoudre le texte au moment de la génération (dans le contexte StackForge, où `I18N` existe) ; le cas `comp.paste_banner` (variable dynamique `pasteAttempts` connue seulement à l'exécution côté élève) traité séparément via un `.replace('{n}', pasteAttempts)` sur le gabarit résolu. `gen-string.js`, qui utilise déjà partout `${I18N.t(...)}` correctement interpolé, n'est pas concerné par ce bug. **Validé par l'utilisateur en conditions réelles Moodle** après ce 4ᵉ correctif.

37.**[Piège systémique identifié, applicable à TOUS les types] Un correctif de code sur un générateur n'a aucun effet sur les questions déjà créées dans l'éditeur, tant qu'elles ne sont pas explicitement régénérées.** Symptôme rapporté par l'utilisateur : test Moodle réel (import du XML exporté par StackForge) montrant encore l'ancienne architecture à deux inputs (`ans1a`/`ans1b`, `lentille_rays()`/`lentille_pts()`/`miroir_rays()`/`miroir_pts()`) sur les questions Optique, alors même qu'un rechargement forcé (Ctrl+F5) puis un nouvel export avaient été effectués — ce qui semblait au premier abord contredire le fait que `js/gen-optique.js` avait déjà été corrigé pour l'architecture à un seul input. Deux fausses pistes écartées avant le bon diagnostic : (1) hypothèse d'un fichier XML de test resté sur le disque (`test/mise à jour/...`) — infirmée par l'utilisateur ("non je viens de l'importer") ; (2) recherche d'un chemin de code résiduel utilisant encore l'ancienne architecture — grep du dépôt entier confirmant qu'aucun fichier vivant ne contient plus `lentille_rays`/`miroir_pts`/etc. **Cause réelle** : `js/editor.js` (`saveEditorState()`, ~ligne 502) sérialise l'objet `questions` complet dans `localStorage['v4_questions']` à chaque modification, et le recharge automatiquement au chargement de la page (~lignes 513-515). Un rechargement forcé (Ctrl+F5) ne vide que le cache HTTP du navigateur, **pas** le `localStorage` du site — donc les questions déjà générées sous l'ancienne version du générateur (avec leur `kbdRaw`/`tans`/`inputXML` figés au moment de leur création) sont restaurées telles quelles, même après correction du code source. Confirmé via `js/config-panel.js` (`_generateAndStoreQuestion`) : une régénération explicite d'une question (rouvrir le panneau de config et cliquer sur générer/mettre à jour) appelle bien le générateur à jour et écrase `questions[qid]` avec du contenu frais — le bug n'est donc pas dans le générateur, mais dans l'absence d'invalidation automatique du cache après une mise à jour de code. **Aucune correction de code appliquée** (risque de casser la persistance légitime entre sessions de travail) — **mitigation manuelle actuelle** : après toute modification d'un fichier `gen-*.js`, régénérer explicitement chaque question concernée via le panneau de configuration avant de ré-exporter, plutôt que de se fier à un simple rechargement de page. Piste évoquée mais non développée : un bouton "Régénérer tout" ou une invalidation automatique par empreinte de version du générateur dans `js/config-panel.js`/`js/editor.js`.

### Phase 1 — Consolidation et stabilisation

Objectif: rendre le cœur de StackForge fiable avant toute extension serveur ou IA. Contient l'audit round-trip ci-dessus (1.1), ses corrections (1.2), les tests XML Moodle/STACK (1.3, voir tableau "État par type" ci-dessus pour les résultats à jour), et le gel des formats JSON (1.4, à faire une fois les types audités — base du futur prompt système IA de la Phase 4).

### Phase 2 — Infrastructure serveur

Objectif: sortir du modèle localStorage/fichier local pour un usage institutionnel.

| Ressource | Spécification | Priorité |
|---|---|---|
| Hébergement statique | nginx, ~500 Mo, HTTPS | Indispensable |
| Conteneur Goemaxima | 1 vCPU, 512 Mo RAM, port REST | Indispensable |
| Backend API | 1 vCPU, 1 Go RAM, Node.js ou Python/FastAPI | Indispensable |
| Base de données | PostgreSQL, ~5 Go | Indispensable |
| Authentification | ProConnect / ENT académique | Indispensable |
| API IA | Albert (DINUM) ou proxy institutionnel | Nécessaire pour Phase 4 |

Ressources à soumettre à la forge des numériques. ⚠️ Les données pédagogiques ne doivent pas transiter par des services IA externes (OpenAI, Anthropic) sans accord institutionnel explicite.

### Phase 3 — Intégration Moodle / LTI 1.3

Objectif: StackForge accessible depuis Moodle sans installation complexe. Architecture retenue: LTI 1.3 + plugin local Moodle minimal — StackForge comme outil externe LTI 1.3, Deep Linking (insertion directe dans un cours Moodle), plugin local Moodle (~50 lignes PHP) pour l'enregistrement automatique de l'outil, API Web Services Moodle pour push/pull vers la banque de questions STACK, Goemaxima pour la validation Maxima temps réel dans l'éditeur Expert.

Statut: aucune étape commencée — squelette backend LTI 1.3 (Node.js), handshake LTI 1.3/OIDC, plugin local Moodle PHP, connexion API Web Services Moodle, push/pull question banque Moodle, proxy Goemaxima.

### Phase 4 — Assistant IA pédagogique

Objectif: l'enseignant dépose son cours ou TP, l'IA propose des questions StackForge configurées.

Flux cible: (1) l'enseignant dépose un document (PDF/DOCX/TXT); (2) StackForge extrait le texte côté client (PDF.js); (3) envoi à l'API IA avec un prompt système décrivant chaque module + son format JSON; (4) l'IA retourne une liste structurée (type, justification pédagogique, JSON pré-rempli); (5) l'enseignant valide chaque suggestion → question créée dans l'éditeur; (6) génération XML habituelle.

Prérequis bloquants: formats JSON documentés (après Phase 1.4, 🔲), accès API IA institutionnelle (Phase 2, 🔲), extraction texte PDF (PDF.js à intégrer, 🔲).

Statut: aucune étape commencée — modale "Analyser un document" (UI + upload), intégration PDF.js, rédaction du prompt système IA (après gel des formats 1.4), connexion API Albert/proxy IA, rendu des suggestions avec aperçu, injection des questions approuvées dans l'éditeur.
