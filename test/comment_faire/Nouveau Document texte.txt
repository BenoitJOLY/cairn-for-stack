### Mise à jour du document des RÈGLES ABSOLUES

**RÈGLES ABSOLUES À RESPECTER (NE PAS DÉVIER) :**

**SYNTAXE GÉNÉRALE MAXIMA :**
*   **Pas de point-virgule (`;`)** : Jamais de `;` à la fin des lignes dans `<questionvariables>`. On utilise UNIQUEMENT `$` pour terminer une instruction.
*   **Une seule instruction par ligne** : JAMAIS de `instr1$ instr2$` sur la même ligne, surtout à l'intérieur d'un `block(...)` ou d'une boucle `do(...)`. Cela provoque l'erreur fatale `"Expected... but ';' found"`. Chaque `$` doit avoir son propre retour à la ligne.
*   **Pas de syntaxe dynamique** : Ne JAMAIS stocker un opérateur (`and`, `or`) dans une variable pour l'évaluer. Faire une liste explicite de toutes les expressions possibles et utiliser `rand()` pour choisir un index.
*   **Simplicité** : Ne JAMAIS utiliser `:=` pour créer des fonctions dans les variables de question. Utiliser uniquement des affectations `:` ou des `makelist(if...then...else...)`.

**TABLES DE VÉRITÉ :**
*   **Pas de `T[i]` pour les tables** : Ne JAMAIS accéder à une table Maxima avec des crochets. Utiliser obligatoirement la syntaxe `Rows : args(truth_table(...))` puis `last(Rows[i])`.
*   **Le piège mortel de `boolean_form()`** : Ne JAMAIS passer le résultat de `boolean_form()` à `truth_table()`. Si l'expression est une tautologie ou une contradiction, `boolean_form()` la simplifie en la constante `true` ou `false`, ce qui fait crasher `truth_table(true)` ("invalid index..."). Utiliser TOUJOURS `truth_table(expr)` directement avec l'expression littérale.
*   **Pas d'évaluation logique partielle** : Ne pas utiliser `if is(ev(expr, P=false...)) then...` car `is(ev(...))` peut rester en suspend et s'afficher en texte brut dans la page HTML.

**INPUTS DE TYPE DROPDOWN (MÉGA PIÈGE) :**
*   **Où mettre la liste ?** : La liste de choix `[[id, bool, "texte"], ...]` va EXCLUSIVEMENT dans le champ **Modèle de réponse (`<tans>`)**.
*   **Options supplémentaires** : Le champ `<options>` dans le XML doit être **OBLIGATOIREMENT VIDE** (laisser `<options></options>`).
*   **Les ID sont des STRINGS** : Les identifiants doivent OBLIGATOIREMENT être des chaînes de caractères : `["1", true, "..."]` et JAMAIS des entiers `[1, true, "..."]`.
*   **Booléens en DUR** : Ne JAMAIS mettre d'expression logique directement dans la liste (ex: `idx_b=1`). Soit utiliser `if idx_b=1 then true else false`, soit (plus sûr) créer 4 listes statiques `choix1, choix2...` avec des `true`/`false` écrits en dur, puis faire `if idx=1 then choix1 elseif idx=2 then choix2...`.
*   **Pas de LaTeX (`tex()`)** : Ne JAMAIS utiliser `tex()` pour générer le texte des options. MathJax ne parse pas le contenu des balises HTML `<option>`. Utiliser du texte Unicode pur (`∧`, `∨`, `¬`, `⇒`).
*   **Récupérer la bonne réponse dans le PRT** : Utiliser exactement cette syntaxe dans les *Feedback variables* du PRT : `vraie_id : first(first(sublist(choix, lambda([ex], second(ex)=true))))$`.

**JSXGRAPH & INTERFACE :**
*   **Pas de `.moveTo()`** : Ne JAMAIS utiliser `.moveTo()` ou `.setAttribute()` dans la fonction `bd.update()` de JSXGraph (risque de boucle infinie).
*   **Limites JS** : Mettre `numberPoints: 150` maximum pour les courbes.

**UNITÉS & DIVERS STACK :**
*   **Unités STACK** : Pour comparer des unités, appliquer `stack_unit_si_to_si_base()` sur la réponse de l'élève ET sur la réponse du prof avant de faire l'extraction avec le `subst(map(lambda...))`.
*   **Pas de `scientificnotation` dans le XML** : Supprimer cette balise du XML pour éviter les crashes d'import, la régler dans l'interface Moodle.
*   **Pas de balises en double** : Vérifier qu'il n'y a qu'un seul `<truefeedback>` ou `<falsefeedback>` par nœud de PRT.
