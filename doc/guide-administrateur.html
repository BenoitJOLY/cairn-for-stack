Cairn for Stack V1 — Guide administrateur

Déployer, configurer et exploiter une instance Cairn for Stack auto-hébergée

Version 2.1 · 2026 Docker · Node.js/Express

1. Introduction

Ce guide s'adresse à la personne qui installe, configure et exploite une instance Cairn for Stack pour un établissement, une équipe ou un usage personnel hébergé. Il ne couvre pas la création de questions STACK elle-même — voir le Guide enseignant pour cet usage.

Deux modes de fonctionnement
  • Mode local (sans serveur) — ouvrir directement index.html dans un navigateur. Aucune authentification, aucun compte, aucune donnée partagée : chaque enseignant utilise son propre poste et sa propre clé IA/Maxima. Ce guide ne s'applique pas à ce mode.
  • Mode hébergé (serveur Node) — l'application tourne derrière un serveur Express qui impose une authentification par compte, centralise la configuration (serveur Maxima, IA, dépôt GitHub) et gère les rôles. C'est ce mode que couvre ce guide.

En mode hébergé, toute l'application est servie derrière un login : aucune page (hormis login.html/register.html et leurs assets) n'est accessible sans session valide.

2. Architecture

L'instance hébergée repose sur trois briques :

  • Frontend statique — HTML/CSS/JS pur (index.html, js/, css/, lang/, lib/), servi par le serveur Node une fois la session authentifiée.
  • Serveur Node/Express (server/) — authentification par session (cookie httpOnly/secure), routage des pages protégées, endpoint de génération sécurisée POST /api/generate, panneau d'administration, relais vers le moteur Maxima.
  • Conteneur Maxima/Stack-API — moteur de calcul formel externe (image stackmaths/stackapi), joint via un réseau Docker partagé pour la prévisualisation réelle et le calcul des deployedseed.
Pourquoi un relais côté serveur vers Maxima ?
Le navigateur n'appelle jamais directement le conteneur Maxima/Stack-API : la route POST /stack-api/:route (liste blanche : render, grade, validate, diff) sert de proxy interne. Cela évite les blocages CORS liés à un port différent et n'expose pas Stack-API comme proxy ouvert vers le réseau interne.

Persistance des données

Toutes les données propres à l'instance (comptes, quotas, configuration, secrets chiffrés) vivent dans server/data/ sous forme de fichiers JSON :

FichierContenu
accounts.jsonComptes (identifiant, hash bcrypt du mot de passe, rôle, indicateur auto-inscrit, clé IA personnelle chiffrée)
usage.jsonHorodatages de génération par compte auto-inscrit, pour le quota hebdomadaire glissant
instance-config.jsonRéglages d'instance (zone de mutualisation, serveur Maxima par défaut, fournisseur IA, mentions légales) et secrets institutionnels chiffrés (jeton GitHub, clé API IA)

Ce dossier n'est jamais commité dans Git (voir .gitignore) : il contient des identifiants et des secrets propres à chaque déploiement.

3. Installation Docker

Prérequis

  • Docker & Docker Compose (le projet a été conçu et éprouvé pour un auto-hébergement sur NAS Synology, mais fonctionne sur toute machine Docker)
  • Un conteneur Maxima/Stack-API déjà fonctionnel, sur un réseau Docker nommé maxima_default (créé par son propre projet Compose)

Étapes

Cloner le dépôt sur la machine hôte : git clone <url-du-depot> && cd cairn-for-stack
Créer un fichier .env à la racine (jamais commité) contenant au minimum SECRETS_KEY, et si souhaité un premier compte admin (voir section suivante).
Vérifier que le réseau maxima_default existe déjà (docker network ls) — docker-compose.yml le rejoint en external: true, il n'est pas recréé.
Construire et démarrer : docker-compose up -d --build
Vérifier la santé du conteneur : curl http://localhost:3000/healthz doit répondre ok.
Se connecter sur http://<hôte>:3000/login.html avec le premier compte admin.
Mise à jour de code sans reconstruction
Le docker-compose.yml monte index.html, depot.html, admin.html, validation.html, login.html, register.html ainsi que js/, css/, lang/, lib/, assets/ et server/ en volumes depuis l'hôte. Une simple mise à jour de fichier sur l'hôte suffit donc pour la plupart des changements — seul un changement dans server/package.json (nouvelle dépendance) exige un docker-compose up -d --build.

Reverse proxy

Si l'instance est exposée derrière un reverse proxy qui termine le HTTPS (par exemple le proxy inversé d'un NAS Synology/DSM), le serveur active app.set('trust proxy', 1) : c'est nécessaire pour que le cookie de session secure se pose correctement malgré une connexion interne en HTTP entre le proxy et le conteneur. Aucune configuration supplémentaire n'est requise côté Cairn for Stack, mais le proxy doit transmettre l'en-tête X-Forwarded-Proto.

4. Variables d'environnement

VariableRôleDéfaut / obligatoire
PORTPort d'écoute du serveur Express3000
SECRETS_KEYClé source du chiffrement AES-256-GCM des secrets institutionnels (jeton GitHub, clé API IA)Obligatoire dès qu'un secret est configuré — sinon erreur explicite au moment d'enregistrer
SESSION_SECRETClé de signature des cookies de sessionGénéré aléatoirement à chaque démarrage si absent
ACCOUNT_USERNAMEIdentifiant du premier compte, créé automatiquement au démarrage du conteneurOptionnel
ACCOUNT_PASSWORDMot de passe du premier compteOptionnel
ACCOUNT_ROLERôle du premier compte (admin, validateur, ou vide)Optionnel
SESSION_SECRET non fixé = déconnexion de tous les comptes à chaque redémarrage
Si SESSION_SECRET n'est pas défini, le serveur en génère un nouveau à chaque démarrage (crypto.randomBytes) : tous les cookies de session existants deviennent invalides et chaque utilisateur doit se reconnecter. Pour une instance en production, fixez une valeur stable dans .env.
SECRETS_KEY : à ne jamais perdre ni changer sans précaution
Les secrets institutionnels (jeton GitHub, clé API IA) sont chiffrés au repos avec une clé dérivée de SECRETS_KEY. Si cette variable change ou disparaît, les secrets déjà enregistrés deviennent indéchiffrables — il faut alors les ressaisir depuis le panneau d'administration après avoir fixé la nouvelle valeur.

Exemple de fichier .env minimal pour une première mise en route :

# .env — jamais commité
SECRETS_KEY=une-chaine-longue-et-aleatoire
SESSION_SECRET=une-autre-chaine-longue-et-aleatoire
ACCOUNT_USERNAME=admin
ACCOUNT_PASSWORD=mot-de-passe-initial
ACCOUNT_ROLE=admin

5. Rôles disponibles

RôleAccès
Enseignant (aucun rôle)Générateur de questions, dépôt pour validation (depot.html), génération IA, clé IA personnelle. Pas d'accès à /admin.html ni /validation.html.
validateurTout ce que fait un enseignant, plus /validation.html : lister, relire, valider ou rejeter les dépôts en attente dans la zone de mutualisation GitHub.
adminAccès complet, y compris /admin.html. Un admin est un sur-ensemble du rôle validateur : il contrôle déjà le jeton GitHub institutionnel utilisé par la promotion, lui refuser l'accès à la file de validation n'apporterait aucune barrière réelle.

Un compte n'a qu'un seul rôle à la fois (pas de cumul admin+validateur explicite — inutile puisque admin inclut déjà validateur).

6. Créer des comptes

Cairn for Stack est pensé pour une liste fermée de comptes créés par l'administrateur, en complément (optionnel, voir section suivante) d'une auto-inscription publique limitée par quota.

Depuis la ligne de commande (SSH dans le conteneur)

sudo docker exec -it cairn-for-stack node server/create-account.js <identifiant> <mot_de_passe> [admin|validateur]

Le rôle est optionnel : un compte créé sans troisième argument est un enseignant classique.

Pour changer le rôle d'un compte existant :

sudo docker exec -it cairn-for-stack node server/set-role.js <identifiant> <admin|validateur|none>

Depuis le panneau d'administration

La section Comptes & rôles de /admin.html liste tous les comptes existants et permet de changer leur rôle par un simple menu déroulant — aucun accès SSH n'est requis pour cette opération. Voir §8.6.

Premier compte admin au démarrage
Renseigner ACCOUNT_USERNAME, ACCOUNT_PASSWORD et ACCOUNT_ROLE=admin dans .env avant le tout premier docker-compose up crée ce compte automatiquement à chaque démarrage du conteneur (l'opération échoue silencieusement — || true — si le compte existe déjà, ce qui la rend sûre à laisser en place durablement).

7. Auto-inscription & quota

En plus des comptes créés par l'administrateur, la page /register.html (endpoint POST /api/register) permet à quiconque connaît l'URL de l'instance de créer son propre compte (identifiant ≥ 3 caractères, mot de passe ≥ 8 caractères). Ces comptes sont marqués selfRegistered et soumis à un quota hebdomadaire de 5 générations (fenêtre glissante de 7 jours), contrairement aux comptes créés via create-account.js qui n'ont aucune limite.

Pas de bascule pour désactiver l'auto-inscription
Il n'existe actuellement aucun réglage pour fermer /register.html : l'endpoint est toujours actif. Pour une instance strictement fermée, restreignez l'accès réseau à l'URL (pare-feu, VPN, IP autorisées) plutôt que de compter sur une option applicative.

Le quota peut être identifié dans server/usage.js (WEEKLY_LIMIT = 5) — une modification de cette constante nécessite une reconstruction ou une simple modification de fichier montée en volume, selon la méthode de déploiement.

8. Panneau d'administration

Accessible sur /admin.html pour tout compte de rôle admin. Chaque section se sauvegarde indépendamment via son propre bouton Enregistrer.

8.1 Zone de mutualisation

Dépôt GitHub utilisé par la fonction « Déposer pour validation » côté enseignant et par la banque de questions validées :

  • Propriétaire / dépôt — owner/repo GitHub cible
  • Branche de dépôt et dossier « à valider » — où atterrissent les dépôts enseignants en attente de relecture
  • Branche banque et dossier banque — où sont déplacées les questions validées

Ces six champs doivent tous être renseignés pour que le workflow de validation (§9) fonctionne : une valeur manquante bloque la promotion avec un message explicite.

8.2 Serveur Maxima / JSmol (défaut d'instance)

URL du serveur Stack-API utilisée comme valeur par défaut quand un enseignant n'a pas configuré son propre serveur dans ses réglages personnels. Utile pour fournir un serveur prêt à l'emploi à toute une équipe sans configuration individuelle.

8.3 Fournisseur IA institutionnel

Configuration compatible API OpenAI (chat completions), utilisée par la génération IA en priorité, avant la clé personnelle de chaque enseignant :

  • URL de base de l'API et modèle — champs non secrets, visibles par tout compte connecté
  • Clé API IA — secret, jamais renvoyé au navigateur une fois enregistré (badge « Configuré »/« Non configuré » uniquement)
Cascade de résolution
server/ai-generate.js résout les identifiants dans cet ordre : clé institutionnelle → clé personnelle du compte → repli vers le flux manuel (copier/coller dans le prompt) si aucune des deux n'est configurée. La génération IA v1 est scopée aux types RA (radio/algébrique) et DD (drag & drop).

8.4 Jeton GitHub institutionnel

Jeton personnel GitHub (PAT) utilisé exclusivement côté serveur, jamais envoyé au navigateur, pour la promotion des dépôts validés vers la banque (server/gh-validation.js). Doit disposer des droits d'écriture (contents) sur le dépôt de mutualisation configuré en §8.1.

Distinct du jeton personnel que chaque enseignant peut saisir côté client pour son propre dépôt initial (« Déposer pour validation ») — celui-ci reste inchangé et n'a jamais transité par le panneau admin.

8.5 Mentions légales & RGPD (instance hébergée)

Ce bloc alimente la modale « Mentions légales » affichée dans l'application cliente. Trois champs sont obligatoires (marqués *) et rejetés côté serveur s'ils sont vides, même en cas d'appel direct à l'API contournant le formulaire :

  • Responsable de traitement (nom/organisme) et e-mail de contact
  • Autorité de contrôle compétente (nom ; URL optionnelle)
Le responsable de traitement, c'est vous — jamais l'auteur du logiciel
Cairn for Stack est un logiciel libre (AGPL-3.0) ; l'auteur du code n'est en aucun cas responsable de traitement des données d'une instance qu'il n'héberge pas. La personne ou l'organisme qui déploie et administre cette instance est seul responsable de traitement au sens RGPD, et doit renseigner ses propres coordonnées et son autorité de contrôle nationale (CNIL en France — Cairn for Stack étant destiné à des déploiements internationaux, ce champ est libre).

Une instance peut proposer plusieurs langues d'interface, mais le responsable et l'autorité de contrôle ne changent pas selon la langue affichée : ils doivent être nommés explicitement plutôt que de laisser un texte générique.

8.6 Comptes & rôles

Tableau de tous les comptes existants (identifiant, rôle, statut auto-inscrit). Le rôle se change directement via un menu déroulant par ligne — pas de bouton « Enregistrer » global, chaque changement est appliqué immédiatement.

9. Workflow dépôt → validation

Un enseignant dépose une question depuis depot.html : elle atterrit dans le dossier « à valider » (sous-dossier par pays) de la branche de dépôt configurée en §8.1, via son propre jeton GitHub personnel côté client.
Un compte validateur (ou admin) ouvre /validation.html, qui liste les dépôts en attente.
La relecture se fait sur un Moodle réel, hors Cairn for Stack — il n'existe pas de prévisualisation in-app pour cette étape.
Valider déplace le fichier vers la banque (PUT sous le dossier banque puis DELETE de l'original, via le jeton institutionnel côté serveur) ; Rejeter le supprime définitivement de la zone de relecture.
Un échec partiel de promotion laisse un message explicite
Si le PUT vers la banque réussit mais que le DELETE de l'original échoue, le dépôt reste visible en double (dans la banque et dans la zone de relecture) plutôt que de tenter un rollback automatique — un message d'erreur invite à réessayer ou nettoyer manuellement. C'est un choix délibéré : un doublon inoffensif est préférable à une logique de rollback complexe et potentiellement fragile.

Par sécurité, un validateur ne peut agir que sur des chemins situés sous le dossier de relecture configuré, même via un appel direct à l'API (assertUnderReviewFolder dans server/gh-validation.js).

10. Sécurité & secrets

Mots de passe et sessions

  • Mots de passe hachés avec bcrypt (coût 12) — jamais stockés en clair.
  • Sessions par cookie httpOnly, secure, sameSite=lax, durée de vie 30 jours.
  • Le middleware d'authentification protège toute la surface applicative (pages et API) hors login.html, register.html et leurs assets.

Secrets institutionnels

Le jeton GitHub et la clé API IA institutionnels sont chiffrés au repos en AES-256-GCM, avec une clé dérivée par SHA-256 de la variable d'environnement SECRETS_KEY (voir §4). Contrat write-only respecté à tous les niveaux : l'API et le panneau d'administration ne renvoient jamais un secret en clair, seulement un booléen « configuré / non configuré ».

Clé IA personnelle (par enseignant)

Chiffrée avec le même mécanisme, stockée dans l'enregistrement du compte concerné (accounts.json). Un enseignant peut l'effacer lui-même depuis l'application ; un administrateur n'a pas de moyen de la lire, seulement de constater si elle est configurée via l'API interne.

11. RGPD — droit à l'effacement

Chaque utilisateur dispose d'un auto-service de suppression de compte, accessible depuis la modale « Mentions légales » de l'application (POST /api/account/delete). Le mot de passe est redemandé avant l'action, car le cookie de session seul ne suffit pas à confirmer une action destructive.

La suppression purge à la fois accounts.json (le compte) et usage.json (l'historique de quota associé), puis détruit la session en cours. Aucune intervention administrateur n'est nécessaire pour honorer une demande de suppression déposée par ce canal.

13. Sauvegarde des données

Le seul répertoire à sauvegarder pour préserver comptes, quotas et configuration d'instance est server/data/ sur l'hôte (monté en volume via ./server:/app/server). Une simple copie de ce dossier suffit à restaurer une instance à l'identique sur une nouvelle machine, à condition de conserver la même valeur de SECRETS_KEY — sans quoi les secrets institutionnels chiffrés deviennent illisibles (voir §4).

Ce qui n'a pas besoin d'être sauvegardé séparément
Le code applicatif (frontend et serveur) vit dans le dépôt Git — seule la donnée d'exploitation propre à l'instance (server/data/) et le fichier .env sont spécifiques au déploiement et absents du contrôle de version.

14. Dépannage / FAQ

« SECRETS_KEY manquant » lors de l'enregistrement d'un secret

La variable d'environnement SECRETS_KEY n'est pas définie sur le conteneur. Ajoutez-la dans .env puis redémarrez (docker-compose up -d). Sans elle, aucun secret institutionnel (jeton GitHub, clé API IA) ne peut être chiffré ni déchiffré.

Tous les utilisateurs sont déconnectés après un redémarrage

SESSION_SECRET n'est probablement pas fixé : le serveur en régénère un aléatoirement à chaque démarrage, ce qui invalide tous les cookies existants. Fixez une valeur stable dans .env (voir §4).

« stack-api injoignable » lors de la génération ou de l'aperçu

Le conteneur Cairn for Stack n'arrive pas à joindre maxima-stack-api-1 sur le réseau Docker maxima_default. Vérifiez que ce conteneur tourne, que le réseau existe (docker network ls) et que le service Cairn for Stack du docker-compose.yml le rejoint bien dans sa section networks.

Un enseignant auto-inscrit ne peut plus générer de questions

Il a probablement atteint le quota hebdomadaire de 5 générations (fenêtre glissante de 7 jours), réservé aux comptes créés via /register.html. Les comptes créés par un administrateur (create-account.js) n'ont pas cette limite — envisagez d'en créer un si l'usage est légitime et récurrent.

La promotion d'un dépôt vers la banque échoue avec « Zone de mutualisation incomplète »

Un des six champs de la zone de mutualisation (propriétaire, dépôt, branches, dossiers) est vide dans le panneau d'administration. Tous sont requis pour que server/gh-validation.js puisse construire les appels à l'API GitHub.

« Jeton GitHub institutionnel non configuré »

Le jeton utilisé pour la promotion des dépôts validés (rôle validateur/admin) est distinct du jeton personnel qu'un enseignant saisit pour son propre dépôt initial. Il se configure exclusivement dans /admin.html → Jeton GitHub institutionnel, avec des droits d'écriture sur le dépôt de mutualisation.

Comment retirer les droits admin à un compte ?

Depuis /admin.html → Comptes & rôles, sélectionner « Enseignant » dans le menu déroulant de la ligne concernée, ou en SSH : node server/set-role.js <identifiant> none. Veillez à toujours conserver au moins un compte admin actif.
